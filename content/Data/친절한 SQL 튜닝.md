# 인덱스

### 인덱스 튜닝
    1. 인덱스 스캔 효율화 튜닝
    2. 랜덤 액세스 최소화 튜닝
- SQL 튜닝은 랜덤 I/O와의 전쟁이다.
- DBMS에서 제공하는 대부분의 기능들은 랜덤 I/O를 줄이는데 목적이 있다.
- 인덱스 컬럼을 가공하지 않아야 인덱스를 정상적으로 사용(Range Scan)할 수 있다.
    - where 해서 비교하는 부분에 substring, upper, 연산 등을 적용해서 진행하는 것, 순수 컬럼 값 그대로 비교하지 않으면 인덱스를 사용하지 못한다.
- 스칼라 서브쿼리?
- Range Scan을 하기 위해서는 선두 컬럼은 가공되지 않은 상태로 조건절에 있어야 한다.
- ‘인덱스를 탄다’는 표현은 ‘인덱스를 Range Scan한다’와 같은 의미인 셈이다.
- 인덱스를 Range Scan 할 수 있는 이유는 데이터가 정렬되어 있기 때문이다.
- 테이블과 달리 인덱스는 정렬되어 있다.
- 인덱스는 기본적으로 정렬되어 있기 때문에, 해당 정렬을 ORDER BY로 명시해 주더라도, 실행 계획에서는 생략되는 경우가 있다.
- 오라클은 허용되는 경우의 타입은 알아서 형 변환하여 처리한다.
- 자동 형변환에 의존해서 할 경우 문제가 발생할 확률이 높으니, 명시적으로 정확히 형변환을 해주는 것이 좋다.
    - TO_CHAR, TO_DATE, TO_NUMBER를 쓸 경우 연산 횟수가 증가한다고 생각하는데, 이를 하지 않더라도 어차피 옵티마이저가 자동으로 생성해서 진행하게 되기 때문에 제대로 사용해주는 것이 좋다.
- 인덱스 스캔 종류
    - Index Range Scan
    - Index Full Scan
    - Index Unique Scan
    - Index Skip Scan
    - Index Fast Full Scan
- 인덱스를 생성할 때, 선두 컬럼이 중요하다.
    - **인덱스를 여러 컬럼으로 만들 수 있다.**
    - **그 인덱스에서 가장 앞에 오는 컬럼(선두 컬럼)이 가장 중요하다.**
    - 선두 컬럼이 WHERE 절에 존재해야 인덱스를 정상적으로 사용할 수 있다.
    - 선두 컬럼이 없으면 사용자 입장에서 기대하는 인덱스 효율이 대부분 사라진다.
- 온라인 프로그램, 배치 프로그램의 튜닝
    - 온라인 프로그램은 보통 소량 데이터를 읽고 갱신하므로 인덱스를 효과적으로 활용하는 것이 무엇보다 중요하다.
    - 조인도 대부분 NL 방식을 사용한다.
    - 대량의 데이터를 읽고 갱신하는 배치 프로그램은 항상 전체범위 처리 기준으로 튜닝해야 한다.
    - 처리대상 집합 중 일부를 빠르게 처리하는 것이 아니라 전체를 빠르게 처리하는 것을 목표로 삼아야 한다.
    - 대량의 데이터를 빠르게 처리하려면, 인덱스와 NL 조인보다 Full Scan과 해시 조인이 유리하다.
    - 대량의 배치 프로그램에선 인덱스보다 Full Scan이 효과적이지만, 초대용량 테이블을 Full Scan하면 상당히 오래 기다려야 하고 시스템에 주는 부담도 적지 않다. 따라서 배치 프로그램에서는 파티션 활용 전략이 매우 중요한 튜닝 요소이고, 병렬 처리까지 더할 수 있으면 금상첨화다.

	- 루트 블록 스캔 과정에서 찾았다면 그 직전 레코드가 가리키는 리프 블록으로 내려가야 한다.
	- 리프 블록을 찾고, 그 안에서 다시 스캔 시작점을 찾아 스캔을 시작합니다.
- 인덱스 선행 컬럼이 조건절에 없거나 '=' 조건이 아니면 인덱스 스캔 과정에 비효율이 발생한다.

### 액세스 조건과 필터 조건
- 인덱스 액세스 조건
	- 인덱스 스캔 범위를 결정하는 조건절이다. 인덱스 수직적 탐색을 통해 스캔 시작점을 결정하는데 영향을 미치고, 인덱스 리프 블록을 스캔하다가 어디서 멈출지를 결정하는데 영향을 미치는 조건절이다.
- 인덱스 필터 조건
	- 인덱스를 이용하든 테이블을 Full Scan하든 테이블 액세스 단계에서 처리되는 조건절은 모두 필터 조건이다.
- 테이블 필터조건
	- 쿼리 수행 다음 단계로 전달하거나 최종 결과 집합에 포함할지를 결정한다.
- 옵티마이저 비용 계산 원리
	- 인덱스를 이용한 테이블 액세스 비용은 항상 아래 공식으로 구한다.
	- 비용 = 인덱스 수직적 탐색 비용 + 인덱스 수평적 탐색 비용 + 테이블 랜덤 액세스 비용        = 인덱스 루트와 브랜치 레벨에서 읽는 블록 수 + 인덱스 리프 블록을 스캔하는 과정에 읽는 블록 수 + 테이블 액세스 과정에 읽는 블록 수
- 비교 연산자 종류와 컬럼 순서에 따른 군집성
	- 첫 번째 나타나는 범위검색 조건까지만 만족하는 인덱스 레코드는 모두 연속해서 모여있지만, 그 이하 조건까지 만족하는 레코드는 비교 연산자 종류에 상관없이 흩어진다.
	- ```sql
	  where C1 = 1
	  and C2 <= 'B'
	  and C3 = '나'
	  and C4 between 'a' and 'b'
	  ```
	  C2까지는 연속되어있지만, C3부터 흩어짐
- 위에서 본 것 같은 연속해서 모여있는 부분까지의 조건이 **인덱스 액세스 조건**, 이후부터의 조건이 **인덱스 필터 조건**이 됩니다.

| 구분        | 인덱스 액세스 조건 | 인덱스 필터 조건  |
| --------- | ---------- | ---------- |
| **역할**    | 읽을 범위 결정   | 읽은 것 중 선별  |
| **범위**    | 연속된 블록     | 흩어진 레코드    |
| **성능 영향** | 스캔 범위 좌우   | 테이블 액세스 감소 |
| **조건 위치** | 첫 범위 조건까지  | 첫 범위 조건 이후 |

- 인덱스 스캔 효율성은 인덱스 컬럼을 조건절에 모두 등치(=) 조건으로 사용할 때 가장 좋다.
- between 조건은 IN-List 조건으로 바꿔주면 좋은 효과를 얻는 경우가 있다.
	- 다만 IN-List 개수가 많으면 수직적 탐색이 너무 많이 발생해 between으로 인해 리프 블록을 스캔하는 비효율보다 더 비효율적일 수 있으니 **인덱스 스캔 과정에 선택되는 레코드들이 서로 멀리 떨어져있을 때만 유용하다는 사실도 기억하자.**
- 위 상황에 IN-List대신 Index Skip Scan을 활용하는 방법도 있다.
- IN 조건은 '='이 아니다. IN 조건이 '='이 되려면 IN-List Iterator 방식으로 풀려야 한다. 그렇지 않으면 IN 조건은 필터 조건이다.
- NUM_INDEX_KEYS를 이용해 인덱스 조건으로 어디까지 사용할지 지정할 수 있다.
- LIKE와 BETWEEN은 둘 다 범위 검색 조건으로서 비효율의 원리가 똑같이 적용된다. 하지만 데이터 분포와 조건절 값에 따라 인덱스 스캔량이 서로 다를 수 있다. 결론부터 말하면, **LIKE 보다 BETWEEN을 사용하는게 낫다. 큰 차이가 나지 않을 수 있지만, BETWEEN을 사용하는 것이 적어도 손해는 안본다.**
- 범위검색 조건을 남용할 때 비효율이 생길 수 있다.
- WHERE 절에 조건이 어떤 순서로 쓰여있든, **옵티마이저가 인덱스 구조에 맞춰 재배치**합니다.
	- - **WHERE 절의 순서는 중요하지 않음**?
	- WHERE 절에 어떻게 적혀있든 가지고 있는 인덱스의 순서로 재배치한 뒤 조회를 시작합니다.

### OR 조건 활용
- `WHERE (cust_id is null or 고객ID = cust_id)` 와 같이 옵션 조건 컬럼을 선두에 두고 고객_ID + 거래일자 순으로 인덱스를 구성해도 사용할 수 없다는 문제가 있습니다. 따라서 인덱스 선두 컬럼에 대한 옵션 조건에 OR 조건을 사용해선 안됩니다.
- OR 조건을 활용한 옵션 조건 처리를 정의 하면 다음과 같다.
	- 인덱스 액세스 조건으로 사용 불가
	- 인덱스 필터 조건으로도 사용 불가
	- 테이블 필터 조건으로만 사용 가능
	- 단, 인덱스 구성 컬럼 중 하나 이상이 Not Null 컬럼이면, 18c부터 인덱스 필터 조건으로 사용 가능
	- 이런 특성을 고려한다면 OR 조건을 이용한 옵션 조건 처리는 가급적 사용하지 않아야 한다.
#### LIKE/BETWEEN 조건 활용
- 변별력이 좋은 필수 조건이 있는 상황에서 이를 사용하는 것은 나쁘지 않다. 필수 조건 컬럼을 인덱스 선두에 두고 액세스 조건으로 사용하면 LIKE/BETWEEN이 인덱스 필터 조건이어도 좋은 성능을 낼 수 있기 때문이다.
- LIKE/BETWEEN 패턴을 사용하고자 할 때는 아래 네 가지 경우에 속하는지 반드시 점검해야 한다.

	- NULL 허용 컬럼
	- 숫자형 컬럼
	- 가변 길이 컬럼

#### 인덱스 설계
- 인덱스가 많으면 다음과 같은 문제가 생긴다.
	- DML 성능 저하 ( TPS 저하 )
	- 데이터베이스 사이즈 증가 ( 디스크 공간 낭비 )
	- 데이터베이스 관리 및 운영 비용 상승
- 인덱스 추가는 시스템에 부하를 주고, 인덱스 변경은 운영 리스크가 크다. 시스템 개발 단계에서 인덱스를 최적으로 설계하는 일이 무엇보다 중요한 이유가 바로 여기에 있다.
- 결합 인덱스를 구성할 때 두 가지 기준
	- 조건절에 항상 사용하거나, 자주 사용하는 컬럼을 선정한다.
	- '=' 조건으로 자주 조회하는 컬럼을 앞쪽에 둔다.
- 위의 두 가지 기능이 기본 공식이지만, 그 외의 고려해야 할 판단 기준은 다음과 같이 있다.
	- **수행 빈도**
	- 업무상 중요도
	- 클러스터링 팩터
	- 데이터량
	- DML 부하(= 기존 인덱스 개수, 초당 DML 발생량, 자주 갱신하는 컬럼 포함 여부 등)
	- 저장 공간
	- 인덱스 관리 비용 등
- sort 연산을 생략하기 위한 인덱스
	- '=' 연산자로 사용한 조건절 컬럼 선정
	- order by 절에 기술한 컬럼 추가
	- '=' 연산자가 아닌 조건절 컬럼은 데이터 분포를 고려해 추가 여부 결정
- 결합 인덱스 선택도
	- 인덱스 생성 여부를 결정할 때 선택도가 충분히 낮은지가 중요한 판단기준이다.
	- 선택도(Seletivity)란 **전체 레코드 중에서 조건절에 의해 선택되는 레코드 비율**을 말하며 선택도에 총 레코드 수를 곱해서 카디널리티를 구한다.
	- 인덱스 설계를 할 때 우리가 할 일은 '항상 사용하는' 컬럼을 앞쪽에 두고 그 중 '=' 조건을 앞쪽에 위치시는 것 뿐이다.
- 중복 인덱스 제거
	- x01 - 계약ID + 청약일자
	- x02 - 계약ID + 청약일자 + 보험개시일자
	- x03 - 계약ID + 청약일자 + 보험개시일자 + 보험종료일자
	- 위와 같은 세 개의 인덱스가 존재한다면, x02는 x01을 완전 포함, x03은 x02를 완전 포함하는 관계로 **'완전 중복'** 이라고 부른다. 이럴 때, x01, x02 인덱스는 삭제해도 된다.
	- x01 - 계약ID + 청약일자
	- x02 - 계약ID + 보험개시일자
	- x03 - 계약ID + 보험종료일자
	- x04 - 계약ID + 데이터생성일시
	- 위와 같은 경우는 중복이 아니라 볼 수 있지만, 계약ID의 카디널리티가 충분히 낮다면 사실상 중복이라 볼 수 있다. 예를들어 계약ID의 평균 카디널리티가 5라고 가정하면 뒤의 어떤 조건이 붙더라도 이미 계약ID를 '=' 으로 찾았을 때 다섯건의 데이터만 나오므로 굳이 인덱스를 따로 만들 필요가 없기 때문이다. 이럴 때에는 아래와 같은 인덱스를 하나만 만들면 충분하다. 위와 같은 상황은 불완정 중복이라 생각하면 된다.
	- x01 - 계약ID + 청약일자 + 보험개시일자 + 보험종료일자 + 데이터생성일시 

# 조인
### NL(Nested Loops) 조인
조인의 기본인 NL조인으로 인덱스를 이용한 조인이기 때문에, 인덱스 부분을 알고있다면 이해하기 어렵지 않다.
```
<C, JAVA>
for(i=0; i<100; i++){ --outer loop
	for(i=0; i<100; i++){ --inner loop
		run..
	}
}

<PL/SQL>
for outer in 1..100 loop
	for inner in 1..100 loop
		dbms_output.put_line(outer || ':' || inner)
	end loop;
end loop;
```
NL조인은 위의 중첩 루프문과 같은 수행구조를 사용한다. 위의 예를 실제 sql로 풀어보면 다음과 같이 데이터에 액세스 하는 것을 예상할 수 있다.
```
begin
	for outer in (select 사원번호, 사원명 from 사원 where 입사일자 >= '19960101')
	loop -- outer loop
		for inner in (select 고객명, 전화번호 from 고객 where 관리사원번호 >= outer.사원번호)
		loop -- inner loop
			dbms_output.put_line(outer.사원명 || ':' || inner.고객명 || ':' || inner.전화번호);
		end loop;
	end loop;
end
```

일반적으로 NL조인은 Outer와 Inner 양쪽모두 index를 이용한다. Outer 쪽 테이블은 사이즈가 크지 않다면 인덱스를 이용하지 않을 수 있다. Table full scan을 하더라도 한번만 확인하면 되기 때문이다. 하지만 Inner쪽 테이블의 경우 인덱스를 해야한다. 그렇지 않으면 outer의 size X inner의 size 번을 table full scan을 반복하기 때문이다.

결국 NL조인은 인덱스를 이용한 조인 방식이라고 할 수 있다.
